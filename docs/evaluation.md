# 稳定性评测设计

## 数据集

仓库包含 240 条 JSONL 测试样本，五类故障各 48 条：

| 故障类型 | 核心验证 |
|---|---|
| MISSING_INVOICE | 能否识别缺票并进入补件，而不是继续提交 |
| DUPLICATE_SUBMIT | 相同幂等键重复调用时，外部提交次数是否仍为 1 |
| POLICY_CONFLICT | 超标准费用能否进入人工审批 |
| TOOL_TIMEOUT | 有限重试、Checkpoint、恢复链路是否生效 |
| PROCESS_CRASH | JVM/Worker 中断后能否从最近 Checkpoint 续跑 |

## 指标定义

### 端到端完成率

`最终完成任务数 / 全部评测任务数`。

简历中的 81% -> 93% 应按“基线版本 vs 开启自动恢复版本”做同一批数据对比，不应混用不同样本。

### 自动恢复率

`无需人工介入即从可恢复异常恢复成功的任务数 / 可恢复异常任务数`。

缺票和政策冲突本身通常需要用户或人工决策，因此不应强行计入“应该自动恢复”的分母。

### 并行材料获取耗时

同一个样本分别执行：
1. 串行：邮箱 -> 网盘 -> 差旅；
2. 并行：三个 CompletableFuture 同时执行。

比较端到端 P50/P95，而不是只比较单次最优值。简历中的“典型任务耗时降低 39%”应由固定数据集重复运行后得出。

## 结果文件建议

真实压测后将原始结果保存为：

```text
benchmark/
  baseline-serial.csv
  parallel.csv
  recovery-off.csv
  recovery-on.csv
  summary.json
```

本仓库当前只写实现与可复现实验定义，不伪造真实运行数字；需要简历中的 39%、81% -> 93%、91% 时，应由本地压测输出覆盖 summary。
